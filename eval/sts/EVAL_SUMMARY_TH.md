# สรุปการประเมิน (Evaluation) ระบบ Thai Text-to-SQL บนฐานข้อมูล STS

*แหล่งข้อมูล: `eval/sts/COMPARISON.md` · โมเดลหลัก: `openai/gpt-4o-mini` · ฐานข้อมูลทดสอบ: STS (dev)*

> **สรุปสั้น:** ตัวแปรที่ทำให้ระบบทำงานได้จริงคือ **RAG (การยกตัวอย่างที่คล้ายกันมาใส่ prompt)** — ทำให้ความแม่นยำจาก **3% → 47%** (deepseek ก็เหมือนกัน 13% → 50%) ส่วนกลไกอื่น (การให้โมเดลแก้ SQL เองเมื่อรันไม่ผ่าน) แทบไม่ช่วย · ค่าใช้จ่ายรัน eval ~$1.60 (~56 บาท) · ต้นทุนพัฒนาจริง > $5

---

## 1. Eval นี้คืออะไร ทำไปทำไม

**Takeaway: วัดว่า "ถามเป็นภาษาไทย → ได้คำตอบที่ถูกต้อง" บ่อยแค่ไหน และอะไรทำให้มันดีขึ้น**

- ระบบรับคำถามภาษาไทย (เช่น *"จำนวนนักเรียนปัจจุบันแยกตามโรงเรียน"*) แล้วให้ AI เขียน SQL รันกับฐานข้อมูล STS แล้วคืนผลลัพธ์
- ปัญหา: SQL ที่ AI เขียน **ถูกบ้างผิดบ้าง** — ต้องมีวิธีวัดว่าถูกกี่ % และปรับอะไรถึงจะดีขึ้น
- Eval = ชุดคำถามมาตรฐาน + เฉลย + วิธีให้คะแนนอัตโนมัติ รันซ้ำได้ เทียบ config / เทียบโมเดลได้

---

## 2. ขั้นตอนการทำ Eval (ทำอะไรบ้าง ตามลำดับ)

**Takeaway: สร้างชุดข้อสอบ 30 ข้อ → ให้ AI ตอบทีละข้อผ่าน pipeline เต็ม → เอา SQL ที่ได้ไปรันเทียบกับเฉลย**

### ขั้นที่ 1 — สร้าง "ชุดข้อสอบ" (Golden set) 30 คำถาม

- ไฟล์ `eval/benchmark_sts.json` — แต่ละข้อมี: คำถามภาษาไทย + **SQL เฉลย** (`gold_sql`) + ประเภท
- **เฉลยทุกข้อถูกตรวจแล้วว่ารันได้จริงและคืนอย่างน้อย 1 แถว** บนฐานข้อมูล dev
- **ชุดข้อสอบนี้แยกออกจากชุดตัวอย่างที่ AI ใช้เรียนรู้** (68 ตัวอย่างใน `profiles/sts/examples.json`) — ไม่งั้น AI จะได้เห็นเฉลยตัวเองผ่านระบบ RAG (โกงข้อสอบ)
- 30 ข้อแบ่งเป็น 3 กลุ่มตามความยาก (ดูคำอธิบาย `held_out / paraphrase / novel` ในหัวข้อ 3)

### ขั้นที่ 2 — ให้ AI ตอบทีละข้อ (pipeline เต็ม)

แต่ละคำถามวิ่งผ่านขั้นตอนเดียวกับตอนใช้งานจริง:

1. **ดึง schema** ของฐานข้อมูล STS
2. **RAG retrieval** — ค้นหา (ก) ตัวอย่างคำถาม-SQL ที่คล้ายที่สุด และ (ข) ตารางที่เกี่ยวข้อง เพื่อยัดเข้า prompt
3. **สร้าง prompt** = คำสั่ง + hints + ตัวอย่าง + schema + คำถาม
4. **เรียก LLM** (gpt-4o-mini) ให้เขียน SQL
5. **ตรวจความปลอดภัย** — บล็อกคำสั่งที่ไม่ใช่ `SELECT`
6. **รัน SQL** กับฐานข้อมูล (สิทธิ์อ่านอย่างเดียว)
7. **ถ้ารันไม่ผ่าน** → ส่ง error กลับให้ LLM แก้ แล้วรันใหม่ (สูงสุด `max_retries` ครั้ง)

### ขั้นที่ 3 — ให้คะแนน (อัตโนมัติ)

- รัน **SQL ที่ AI เขียน** และ **SQL เฉลย** แล้วเอา **ผลลัพธ์ (ตารางแถว)** มาเทียบกัน
- เทียบแบบไม่สนลำดับแถว, ตัวเลขทศนิยมปัดเป็น 2 ตำแหน่ง
- ได้ค่าหลายตัว (EX, relaxed, grain, first-try...) — อธิบายในหัวข้อ 3

### ขั้นที่ 4 — การทดลอง (Ablation) ปรับทีละตัวแปร

รันชุดข้อสอบซ้ำหลายรอบด้วย config ต่างกัน:

| ตัวแปร | ค่าที่ทดลอง | ถามว่า |
|---|---|---|
| `rag_top_k` | 0 กับ 3 | ใส่ตัวอย่าง 3 อัน vs ไม่ใส่เลย ช่วยแค่ไหน |
| `max_retries` | 0 กับ 2 | ให้แก้ SQL เอง vs ไม่ให้แก้ ช่วยแค่ไหน |

= 2 × 2 = 4 config, **รันซ้ำ config ละ 5 รอบ** (กันฟลุ๊ค) = 20 รอบ × 30 ข้อ = **600 ครั้ง**

### ขั้นที่ 5 — รวมผล

`python eval/compare.py` → สรุปเป็นตารางใน `eval/sts/COMPARISON.md` (ค่าเฉลี่ย ± ส่วนเบี่ยงเบนมาตรฐานจาก 5 รอบ)

## 3. คำศัพท์ — ทุกค่าหมายถึงอะไร

**Takeaway: "EX" คือคะแนนหลัก (ตอบถูกเป๊ะ), "relaxed" คือให้อภัยเรื่องคอลัมน์บรรยาย, "grain" คือจำนวนแถวถูก**

### ประเภทคำถาม (ความยาก)

| คำ | จำนวน | หมายถึง | วัดอะไร |
|---|--:|---|---|
| **held_out** | 10 | คำถามที่ดึงออกจากชุดเรียนรู้ แล้ว**ลบออกจาก RAG** — AI ไม่เคยเห็น | การ generalize จริง (ไม่มีตัวช่วย) |
| **paraphrase** | 12 | คำถามเดิมแต่**เขียนใหม่** (ย่อ / พิมพ์ผิด / ไทยปนอังกฤษ) — ตัวพี่น้องยังอยู่ใน RAG | AI ปรับใช้ตัวอย่างที่คล้ายได้แค่ไหน |
| **novel** | 8 | **combination ใหม่** ที่ชุดตัวอย่างไม่เคยมี (metric × การจัดกลุ่ม แบบที่ไม่เคยสอน) | การประกอบความรู้ (ยากสุด) |

### ค่าคะแนน (metrics)

| คำ | ชื่อเต็ม | หมายถึง (ภาษาคน) |
|---|---|---|
| **EX** | Execution Accuracy (strict) | **คะแนนหลัก** — ผลลัพธ์ตรงกับเฉลย**เป๊ะทุกคอลัมน์ทุกแถว** |
| **EX relaxed** | Execution Accuracy (relaxed) | ให้อภัย**คอลัมน์บรรยายเกิน/ขาด 1 คอลัมน์** (เช่น มี `school_name` เพิ่มมาแต่ตัวเลขถูกหมด) — จำนวนแถวต้องตรง เป็น "เพดานบน" ไม่ใช่คะแนนจริง |
| **first-try** | First-try success | ตอบถูกเป๊ะ **โดยไม่ต้อง retry เลย** (ครั้งเดียวผ่าน) |
| **grain** | Grain correct | **จำนวนแถวตรงกับเฉลย** — จับกรณี JOIN ผิดจนแถวบวม (เช่น เฉลย 10 แถว แต่ได้ 47 แถวเพราะ join ซ้ำ) |
| **p50 / p95** | latency percentile | เวลาต่อคำถาม — p50 = ค่ากลาง (ครึ่งหนึ่งเร็วกว่านี้), p95 = 95% เร็วกว่านี้ (ตัวช้าสุด) |

### ประเภทข้อผิด (error classes)

| คำ | หมายถึง |
|---|---|
| **cols_only** | เลขถูก จัดกลุ่มถูก แต่**คอลัมน์บรรยายต่าง** (ผ่าน relaxed แต่ไม่ผ่าน strict) |
| **wrong_grain** | จำนวนแถวผิด (มักเพราะ JOIN ผิด) |
| **wrong_result** | รันได้ แต่**ตัวเลข/ผลลัพธ์ผิด** |
| **exec_fail** | SQL รันไม่ผ่าน (คอลัมน์ไม่มีจริง ฯลฯ) |
| **no_sql** | AI สร้าง SQL ไม่ได้เลย |

### config

| คำ | หมายถึง |
|---|---|
| **RAG** | Retrieval-Augmented Generation — ค้นหาตัวอย่าง/ข้อมูลที่เกี่ยวข้องมาใส่ prompt ก่อนให้ AI ตอบ |
| **rag_top_k** | จำนวนตัวอย่างคำถาม-SQL ที่ดึงมาใส่ prompt (0 = ไม่ใส่, 3 = ใส่ 3 อันที่คล้ายสุด) |
| **retry / max_retries / self-correction** | เมื่อ SQL รันไม่ผ่าน ส่ง error กลับให้ AI แก้แล้วลองใหม่ — สูงสุดกี่ครั้ง |

## 4. ผลลัพธ์

### 4.1 ผลของโมเดลหลัก — gpt-4o-mini (config ดีที่สุด: rag=3, retry=2, เฉลี่ย 5 รอบ)

| ค่า | ผล | แปลว่า |
|---|--:|---|
| EX (strict) | **47% ±4%** | ตอบถูกเป๊ะ ~ครึ่งหนึ่ง |
| EX relaxed | **76% ±3%** | ถ้าไม่ซีเรียสเรื่องคอลัมน์บรรยาย ~3 ใน 4 ใช้ได้ |
| first-try | 44% ±4% | ส่วนใหญ่ที่ถูก ถูกตั้งแต่ครั้งแรก |
| grain | 87% ±4% | จำนวนแถวถูกเกือบตลอด → JOIN ไม่ค่อยพัง |
| held_out | 48% ±4% | คำถามใหม่ที่ไม่มีตัวช่วย |
| paraphrase | **70% ±4%** | คำถามเขียนใหม่ ทำได้ดี |
| novel | **12% ±11%** | combination ใหม่ พังเกือบหมด (แปรปรวนสูง เพราะมีแค่ 8 ข้อ) |
| p50 / p95 latency | 6.6s / 21.2s | ต่อคำถาม |

### 4.2 การทดลอง Ablation — อะไรช่วย อะไรไม่ช่วย

| rag_top_k | retry | EX | EX relaxed | first-try | grain | p50 |
|--:|--:|--:|--:|--:|--:|--:|
| **0** | 0 | **3%** | 30% ±3% | 3% | 70% ±6% | 4.4s |
| **0** | 2 | 5% ±2% | 30% ±4% | 5% ±2% | 69% ±3% | 7.0s |
| **3** | 0 | **47% ±2%** | 73% ±4% | 47% ±2% | 88% ±4% | 6.2s |
| **3** | 2 | 47% ±4% | 76% ±3% | 44% ±4% | 87% ±4% | 6.6s |

**อ่านตารางนี้ว่า:**

- **RAG คือทุกอย่าง:** rag 0 → 3 ทำให้ EX พุ่งจาก **3% → 47%** (relaxed 30% → 76%) — ไม่มีอะไรอื่นขยับได้ใกล้เคียง ตัวอย่าง 3 อันสอนให้ AI รู้วิธี JOIN ตารางของ STS และกฎ "นักเรียนปัจจุบัน" ที่ schema เปล่า ๆ บอกไม่ได้
- **retry แทบไม่ช่วย:** retry 0 → 2 คือ 47% → 47% (relaxed 73% → 76% อยู่ในช่วง noise) เพราะที่ rag=3 SQL รันผ่านอยู่แล้ว 88% → retry ไม่มีอะไรให้แก้ แต่กิน token + เวลา ~3 เท่าในข้อที่มันแตะ → **ค่า default ควรเป็น retry=0**
- **ช่องว่าง strict (47%) กับ relaxed (76%) = การเลือกคอลัมน์ ไม่ใช่การคำนวณ:** ~29 จุดเป็น `cols_only` — เลขถูก จัดกลุ่มถูก แค่มีคอลัมน์บรรยายเกิน/ต่างชื่อ (เช่น `school_name` vs `school_id`) สำหรับ dashboard ใช้ได้ แต่การให้คะแนนแบบตรงเป๊ะจะตก
- **แยกตามความยาก:** paraphrase 70% > held_out 48% > **novel 12%** — AI จัดการคำถามที่เขียนใหม่ได้ดี แต่พังกับ combination ที่ชุดตัวอย่างไม่เคยสอน → ตรงนี้คือจุดที่ต้องเพิ่มตัวอย่าง

### 4.3 การวิเคราะห์ error — แต่ละข้อพลาดเพราะอะไร

รวม 5 รอบ = 150 คำถาม/config

| ประเภท | rag=3, retry=2 | rag=0, retry=2 | หมายถึง |
|---|--:|--:|---|
| **PASS** (ถูกเป๊ะ) | **47%** (71) | 5% (7) | ผ่าน strict EX |
| **cols_only** | **29%** (43) | 25% (38) | เลขถูก จัดกลุ่มถูก คอลัมน์บรรยายต่าง |
| wrong_result | 11% (17) | **39%** (58) | รันได้ แต่ตัวเลขผิด |
| wrong_grain | 3% (5) | **22%** (33) | จำนวนแถวผิด (JOIN ผิด) |
| no_sql | 8% (12) | 3% (4) | สร้าง SQL ไม่ได้ — **ส่วนใหญ่เพราะโดน OpenAI rate-limit** ตอน retry ยิงถี่ (retry=0 เหลือ 3%) |
| exec_fail | 1% (2) | 3% (5) | SQL รันไม่ผ่าน |

**อ่านว่า:**
- **ที่ rag=3 `cols_only` คือ error หลัก (29%)** — ยืนยันว่าจุดอ่อนคือการเลือกคอลัมน์ ไม่ใช่ตรรกะ SQL
- **ที่ rag=0 พังกระจาย** — ตัวเลขผิด 39% + แถวบวมจาก JOIN ผิด 22% (โมเดลไม่รู้ join path)
- `no_sql` 8% ที่ rag=3/retry=2 เป็น **ข้อจำกัดของ harness** (retry ยิง LLM 3 เท่า → ชน rate-limit) ไม่ใช่ความสามารถของโมเดล

## 5. โมเดลที่ 2 — deepseek-v4-flash-0731

**Takeaway: RAG ช่วยแบบเดียวกับ gpt-4o-mini (13% → 50%) · headline เสมอกับ gpt-4o-mini · เก่ง novel มาก · แต่ช้ากว่า 4 เท่า + provider ไม่เสถียร (มี timeout)**

- ทดลองเป็นโมเดลที่ 2 ผ่าน OpenRouter — **รัน 1 รอบต่อ config** (gpt-4o-mini รัน 5 รอบ) → **ยังไม่มี ± ถือเป็น indicative ไม่ใช่คำตัดสิน**
- Provider ของ deepseek บน OpenRouter **ค้างกลางสตรีม** บางคำถาม → ต้องเพิ่ม **per-question timeout 150 วิ** ใน harness (คำถามที่ค้างถูก mark `timeout` = นับเป็นผิด แล้วไปข้อต่อไป)
  - rag=0 โดน timeout **8/30 ข้อ** · rag=3 โดน **1/30**
  - → rag=0 ที่ 13% เป็น **ค่าต่ำสุด** (บาง timeout อาจจะผ่านถ้ามีเวลา) · rag=3 ใกล้ค่าจริง

| config | EX | EX relaxed | first-try | grain | held_out | paraphrase | novel | timeout |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| rag=3, retry=2 | **50%** | 83% | 50% | 97% | 40% | 50% | **62%** | 1/30 |
| rag=0, retry=2 | 13% | 43% | 13% | 70% | 20% | 8% | 12% | 8/30 |

- **RAG ดัน EX 13% → 50%** (relaxed 43% → 83%) — เรื่องเดียวกับ gpt-4o-mini
- **novel 62%** — สูงกว่า gpt-4o-mini (12%) มาก · grain 97% ก็ดีกว่า (87%)

### 5.1 ตารางเทียบ 2 โมเดล (config rag=3, retry=2)

**Takeaway: headline เสมอกัน (50% vs 47%) · deepseek ชนะ novel + grain · gpt-4o-mini ชนะขาดเรื่องความเร็ว + ความเสถียร**

| ค่า | **gpt-4o-mini** | **deepseek-v4-flash-0731** |
|---|--:|--:|
| จำนวนรอบ | 5 รอบ | **1 รอบ** (ไม่มี ±) |
| EX (strict) | 47% ±4% | **50%** |
| EX relaxed | 76% ±3% | **83%** |
| first-try | 44% ±4% | 50% |
| grain | 87% ±4% | **97%** |
| held_out | **48% ±4%** | 40% |
| paraphrase | **70% ±4%** | 50% |
| novel | 12% ±11% | **62%** |
| p50 / p95 latency | **6.6 / 21.2 วิ** | 24.8 / 108.6 วิ |
| timeout (150 วิ) | 0 | 1/30 |
| ราคา in / out (ต่อ 1M tokens) | $0.15 / $0.60 | **$0.05 / $0.16** |
| ค่าใช้จ่าย eval | $1.53 (600 คำถาม) | **$0.07 (60 คำถาม)** |
| สถานะ | ✅ 5 รอบ ครบ | ⚠️ 1 รอบ + provider ค้างบางข้อ |

**อ่านตารางนี้ว่า:**
- **headline เสมอกัน** — EX 50% vs 47% (ต่างในช่วง noise, deepseek ไม่มี ± ด้วย)
- deepseek **ชนะชัดที่ novel (62 vs 12)** และ grain (97 vs 87) — จัดการ combination ใหม่ + JOIN ได้ดีกว่า
- gpt-4o-mini **ชนะขาดที่ paraphrase (70 vs 50)**, ความเร็ว (~4 เท่า), ความเสถียร (deepseek provider ค้าง)
- **ยังตัดสินไม่ได้เต็มปาก** — deepseek ต้องรัน 5 รอบเหมือน anchor + ใช้ provider ที่เสถียร (DeepSeek API ตรง)

## 6. ค่าใช้จ่าย

**Takeaway: เฉพาะ eval ที่ให้คะแนน ~$1.6 (~57 บาท) — แต่ค่าใช้จ่ายจริงของโปรเจกต์ตอนนี้ > $5 เพราะขั้นตอนตั้งค่า/แก้บั๊กใช้โมเดลใหญ่กว่ามาก**

### 6.1 เฉพาะการรัน eval (คิดจาก token ที่ประเมินได้)

| รายการ | จำนวน | ค่าใช้จ่าย (ประมาณ) |
|---|--:|--:|
| **gpt-4o-mini** — sweep เต็ม (4 config × 5 รอบ = 20 รอบ, 600 คำถาม) | 600 | **$1.53 (~54 บาท)** |

**วิธีคิด (± ประมาณ 50% เพราะ eval ไม่ได้บันทึก token จริง):**
- ต่อคำถาม: input ~9,000–10,000 tokens (schema + hints + ตัวอย่าง + คำถาม), output ~200 tokens (ตัว SQL)
- ที่ `retry=2`: มี "การเรียกซ้ำ" เฉลี่ย ~0.7 ครั้ง/คำถาม แต่ละครั้งแนบ schema เต็ม (~18,000 tokens) → cell `rag=0, retry=2` กินงบเยอะสุดเพราะ SQL มั่ว → retry บ่อย
- ราคา gpt-4o-mini: input $0.15 / output $0.60 ต่อ 1 ล้าน tokens
- ราคา deepseek-v4-flash-0731: input $0.05 / output $0.16 ต่อ 1 ล้าน tokens

### 6.2 ค่าใช้จ่ายจริงของโปรเจกต์ (> $5)

ตัวเลข $1.60 ข้างบนคือ **เฉพาะการรัน benchmark ที่ให้คะแนน** เท่านั้น
ค่าใช้จ่ายจริงที่เกิดขึ้นตอนนี้ **มากกว่า $5** — ส่วนที่เกินมาจาก:

- **การตั้งค่า harness + เขียน/แก้บั๊กระหว่างทาง** ใช้โมเดลใหญ่ (ระดับ **Claude Sonnet / GPT-5**) เป็นตัวช่วยเขียนโค้ด eval, สร้าง golden set, ปรับ prompt, วิเคราะห์ error — โมเดลกลุ่มนี้ราคา **สูงกว่า gpt-4o-mini ~20–50 เท่า** ต่อ token
- การรัน eval รอบแรก ๆ ที่เจอบั๊ก (SQL validator บล็อก CTE, schema ไม่ quote คอลัมน์ตัวพิมพ์ใหญ่ ฯลฯ) แล้วต้องรันซ้ำ
- diagnostic calls ตอนโดน OpenAI rate-limit + การลอง deepseek 3 รอบ

ส่วนนี้ไม่ได้นับใน eval เพราะไม่ใช่ "การให้คะแนนโมเดล" แต่เป็นต้นทุนพัฒนาที่เกิดขึ้นจริง
สรุป: **ต้นทุน dev + setup >> ต้นทุนรัน eval** — ถ้ารัน eval รอบเดียวหลังระบบนิ่งแล้ว จะจ่ายแค่ ~$1.5

**ไม่รวม:** embedding model (รันในเครื่อง ฟรี), ค่าโฮสต์ / DB

## 7. สรุปและข้อเสนอ

**Takeaway: ระบบใช้ได้จริงที่ EX ~47% (relaxed 76%) — ควร ship ที่ `rag=3, retry=0` และลงทุนที่ชุดตัวอย่าง ไม่ใช่โมเดลใหญ่**

### สิ่งที่ได้เรียนรู้

- **RAG few-shot เป็นตัวแปรชี้ขาด** — gpt-4o-mini 3% → 47% · deepseek 13% → 50% (เรื่องเดียวกันทั้ง 2 โมเดล)
- **self-correction (retry) ไม่คุ้ม** — ไม่เพิ่มคะแนน แต่เพิ่มเวลา/ค่าใช้จ่าย ~3 เท่า
- **จุดอ่อนหลักของ gpt-4o-mini 2 จุด:** (1) การเลือกคอลัมน์บรรยาย (strict 47% vs relaxed 76%) (2) คำถามแบบ novel (12%) — deepseek ทำ novel ได้ 62% น่าตามต่อ
- **2 โมเดล headline เสมอกัน** (EX 47% vs 50%) — deepseek ชนะ novel/grain, gpt-4o-mini ชนะความเร็ว (4 เท่า) + ความเสถียร

### ข้อเสนอ

| ทำอะไร | เพราะ |
|---|---|
| **ตั้ง default เป็น `rag=3, retry=0`** | retry ไม่ช่วย ประหยัดเวลา/เงิน 2-3 เท่า |
| **เพิ่มตัวอย่างในชุด RAG โดยเฉพาะแบบ novel** | novel = จุดที่พังชัดสุด (12%) และเป็นจุดที่ RAG แก้ได้ |
| **ปรับ prompt เรื่องการเลือกคอลัมน์** (เอาเฉพาะที่ถาม) | ปิดช่องว่าง strict/relaxed 29 จุด |
| **รัน deepseek ครบ 5 รอบ + ใช้ provider ตรง** (DeepSeek API) | 1 รอบยังไม่มี ± · OpenRouter provider ค้าง (rag=3 timeout 1/30, rag=0 8/30) |

### ข้อจำกัดของการทดลองนี้

- ฐานข้อมูล dev มีข้อมูลน้อย (1 ภาคเรียน, 10 โรงเรียน, 6,000 การลงทะเบียน) — ตัวเลขอาจไม่ตรงกับ production
- `novel` มีแค่ 8 ข้อ → ส่วนเบี่ยงเบน ±11% สูงมาก ตีความอย่างระวัง
- **gpt-4o-mini รัน 5 รอบ (มี ±) · deepseek รันแค่ 1 รอบ (ไม่มี ±) + มี timeout** — เทียบ 2 โมเดลยังไม่ final
- ค่าใช้จ่ายเป็นการประมาณ (eval ไม่บันทึก token จริง)
