# รายงานการประเมินระบบ Thai Text-to-SQL บนฐานข้อมูล STS

*เอกสารต้นฉบับสำหรับนำไปทำสไลด์ · อ้างอิง `eval/sts/COMPARISON.md` (เฟส 1) และ `eval/sts/BEFORE_AFTER.md` (เฟส 2) · เฟส 1 รันวันที่ 31 สิงหาคม 2026 · เฟส 2 รันวันที่ 16 กันยายน 2026*

> **สรุปสำหรับผู้บริหาร:** การใส่ตัวอย่าง SQL ที่คล้ายคำถามจำนวน 3 ตัวอย่างผ่าน RAG เป็นปัจจัยที่ช่วยระบบมากที่สุด โดยเพิ่ม Execution Accuracy แบบ strict จาก **3% เป็น 47%** ขณะที่การเปิด retry ไม่ได้เพิ่ม strict accuracy อย่างชัดเจน แต่เพิ่มเวลาและค่าใช้จ่าย การตั้งค่าที่เหมาะกับผลทดลองนี้จึงเป็น **`rag_top_k=3, max_retries=0`** ค่าใช้จ่ายของ sweep ที่รันครบด้วย gpt-4o-mini อยู่ที่ประมาณ **$1.53 หรือ 54 บาท** และเมื่อรวมการทดลอง DeepSeek ที่รันไม่สำเร็จประมาณ **$1.61 หรือ 56–57 บาท**
>
> **เฟส 2 (กันยายน 2026):** เปลี่ยนสถาปัตยกรรมจาก "1 คำถาม 1 SQL" เป็น **conversational agent loop** ตามคำแนะนำของอาจารย์ — บน benchmark ใหม่แบบสมดุล 36 ข้อ agent รักษาความแม่นยำ SQL ได้ระดับ parity (strict EX 57.1% → 53.6% คือ noise ของ single-run) และปลดล็อกความสามารถที่ pipeline เดิมทำไม่ได้เลย: **ปฏิเสธคำขอนอกขอบเขต 0/4 → 4/4 และถามกลับเมื่อคำถามกำกวม 0/4 → 4/4** แลกมาด้วย latency p50 2.3 → 10.5 วินาที

## 1. สมมติฐาน

**ใจความสำคัญ: ต้องการทดสอบว่า RAG few-shot และการให้โมเดลแก้ SQL ซ้ำ ช่วยเพิ่มความถูกต้องของระบบได้จริงหรือไม่**

### คำถามวิจัย

ระบบที่รับคำถามภาษาไทยแล้วสร้าง SQL จะให้คำตอบถูกต้องขึ้นหรือไม่ เมื่อ:

1. นำตัวอย่าง “คำถาม–SQL” ที่คล้ายกันมาใส่ใน prompt ด้วย RAG
2. อนุญาตให้โมเดลแก้ SQL ใหม่ เมื่อ SQL ครั้งแรกเกิด execution error

### สิ่งที่คาดไว้ก่อนทดลอง

- คาดว่า **RAG few-shot จะเพิ่มความแม่นยำ** เพราะ schema บอกเพียงโครงสร้างตาราง แต่ไม่ได้บอกกฎเชิงธุรกิจทั้งหมด เช่น join path ที่ควรใช้ หรือความหมายของ “นักเรียนปัจจุบัน”
- คาดว่า **retry หรือ self-correction อาจช่วยลด SQL ที่รันไม่ผ่าน** เพราะระบบนำ error จากฐานข้อมูลกลับไปให้โมเดลแก้
- สมมติฐานถือว่าได้รับการสนับสนุน หาก config ที่เปิด RAG หรือ retry มีค่า Execution Accuracy สูงกว่า baseline อย่างสม่ำเสมอในการรันซ้ำ 5 รอบ

### ผลตัดสินแบบย่อ

- **RAG: สมมติฐานได้รับการสนับสนุนชัดเจน** — strict EX เพิ่มจาก 3% เป็น 47% เมื่อเปรียบเทียบ `rag=0, retry=0` กับ `rag=3, retry=0`
- **Retry: สมมติฐานไม่ได้รับการสนับสนุนใน workload นี้** — ที่ `rag=3` ค่า strict EX เท่าเดิมที่ 47% เมื่อเพิ่ม retry จาก 0 เป็น 2

## 2. ที่มาและแนวคิด

**ใจความสำคัญ: การดูว่า SQL “รันได้” อย่างเดียวไม่พอ เพราะ SQL อาจรันสำเร็จแต่คืนคำตอบผิด จึงต้องเทียบผลลัพธ์กับ SQL เฉลย**

ระบบ Thai Text-to-SQL ของโครงการนี้รับคำถามภาษาคน เช่น “จำนวนนักเรียนปัจจุบันแยกตามโรงเรียน” แล้วให้ LLM สร้าง SQL เพื่อรันกับฐานข้อมูล STS ปัญหาคือ SQL ที่มี syntax ถูกและรันได้ อาจเลือกตารางผิด, JOIN แล้วเกิดแถวซ้ำ, คำนวณ metric ผิด หรือคืนคอลัมน์ไม่ตรงกับที่ผู้ใช้ถาม

การประเมินจึงใช้แนวคิด **result-set comparison**: รันทั้ง SQL ที่โมเดลสร้างและ SQL เฉลยบนฐานข้อมูลเดียวกัน แล้วเปรียบเทียบตารางคำตอบที่ได้ วิธีนี้ตอบคำถามที่สำคัญกว่า text matching คือ “ถึง SQL จะเขียนคนละแบบ แต่ได้คำตอบเดียวกันหรือไม่”

อีกประเด็นคือการหลีกเลี่ยง **data leakage** หรือการที่โมเดลเห็นเฉลยของข้อสอบผ่านคลังตัวอย่าง RAG โครงการจึงมี benchmark 30 ข้อแยกจากคลังตัวอย่าง 68 ข้อ และจำแนกคำถามตามที่มาว่า `held_out`, `paraphrase` หรือ `novel` เพื่อดูความสามารถคนละด้านของระบบ

## 3. วิธีการทดลอง

**ใจความสำคัญ: สร้างข้อสอบ 30 ข้อ ให้ระบบตอบผ่าน pipeline เดียวกับการใช้งานจริง เปรียบเทียบกับ SQL เฉลย และรันซ้ำ 5 รอบต่อ config**

### 3.1 เตรียม benchmark หรือ “ชุดข้อสอบ”

- ใช้ไฟล์ `eval/benchmark_sts.json` จำนวน **30 คำถาม**
- แต่ละข้อประกอบด้วย `id`, ประเภทคำถาม, คำถามภาษาไทย และ `gold_sql` หรือ SQL เฉลย
- SQL เฉลยถูกเตรียมให้รันกับฐานข้อมูล STS dev
- ชุดข้อสอบแยกจากคลัง RAG `profiles/sts/examples.json` ซึ่งมี **68 ตัวอย่าง** เพื่อไม่ให้ดึงข้อสอบเดียวกันมาเป็นตัวอย่างตอบ

คำถาม 30 ข้อแบ่งตามแหล่งที่มาเป็น 3 กลุ่ม:

| กลุ่ม | จำนวน | ความหมาย | สิ่งที่ต้องการวัด |
|---|---:|---|---|
| `held_out` | 10 | คำถามที่นำออกจากคลังตัวอย่างและไม่ให้ RAG เห็น | ความสามารถตอบคำถามที่ไม่เคยเห็นตรง ๆ |
| `paraphrase` | 12 | ความหมายใกล้ตัวอย่างเดิม แต่เขียนใหม่ เช่น ย่อคำ พิมพ์ผิด หรือไทยปนอังกฤษ | ความสามารถเข้าใจการเขียนหลายรูปแบบและใช้ตัวอย่างใกล้เคียง |
| `novel` | 8 | การจับคู่ metric × ระดับการจัดกลุ่มแบบใหม่ที่ไม่มีในคลังตัวอย่าง | ความสามารถประกอบความรู้เพื่อแก้โจทย์ใหม่จริง ๆ |

> `held_out` อ่านว่า “เฮลด์เอาต์” ไม่ใช่ `helo-out` หมายถึงข้อมูลที่กันไว้สำหรับทดสอบและไม่นำไปเป็นตัวอย่างให้ระบบระหว่าง eval

### 3.2 ให้ระบบสร้างและรัน SQL

แต่ละคำถามผ่านขั้นตอนต่อไปนี้:

1. โหลด schema และ hints ของฐานข้อมูล STS
2. ถ้าเปิด RAG ให้ค้นหาตัวอย่างคำถาม–SQL ที่คล้ายที่สุดจำนวน `rag_top_k` ตัวอย่าง พร้อมเลือก schema ที่เกี่ยวข้อง
3. ประกอบ prompt จากคำสั่ง, hints, ตัวอย่าง RAG, schema และคำถาม
4. เรียก `openai/gpt-4o-mini` เพื่อสร้าง SQL
5. ตรวจความปลอดภัยของ SQL และอนุญาตเฉพาะคำสั่งอ่านข้อมูล
6. รัน SQL กับฐานข้อมูล STS dev
7. ถ้าเกิด execution error และตั้ง `max_retries > 0` ให้นำ error กลับไปให้ LLM แก้ SQL แล้วลองใหม่ สูงสุดตามจำนวน retry ที่กำหนด

คำถามถูกรันแบบ concurrent ครั้งละไม่เกิน 3 ข้อ ส่วนข้อแรกถูกรันเดี่ยวก่อนเพื่อสร้าง schema cache และ RAG index

### 3.3 เปรียบเทียบคำตอบและให้คะแนน

ระบบรัน `gold_sql` และ SQL ที่โมเดลสร้างบนฐานข้อมูลเดียวกัน แล้วเทียบ result set โดยไม่ยึดลำดับแถว ข้อความถูกตัดช่องว่างหัวท้ายและแปลงเป็นตัวพิมพ์เล็ก ส่วนเลขทศนิยมถูกปัดเป็น 2 ตำแหน่งก่อนเทียบ

#### ความหมายของ metrics

| ค่า | ความหมายแบบเข้าใจง่าย | วิธีอ่านค่า |
|---|---|---|
| **EX (strict)** | Execution Accuracy แบบเข้ม: ผลลัพธ์ต้องตรงกับเฉลยทุกแถวและทุกคอลัมน์ | เป็นคะแนนหลัก; 47% หมายถึงเฉลี่ย 47 จาก 100 คำถามได้ result set ตรงทั้งหมด |
| **EX relaxed** | ยอมให้คอลัมน์บรรยายเพิ่มหรือขาดได้ประมาณ 1 คอลัมน์ หากจำนวนแถวและคอลัมน์ส่วนใหญ่ตรง | ใช้ดู “เพดานบน” ของคำตอบที่สาระหลักอาจถูก แต่รูปแบบคอลัมน์ไม่ตรง ไม่ควรใช้แทน strict EX |
| **first-try** | สัดส่วนข้อที่ผ่าน strict EX และถูกตั้งแต่การเรียกครั้งแรก โดยไม่ได้ใช้ retry | สูงแปลว่าระบบไม่ต้องพึ่งการแก้คำตอบซ้ำ |
| **grain** | ใน eval นี้ตรวจแบบ heuristic ว่า **จำนวนแถวของคำตอบเท่ากับเฉลยหรือไม่** | ช่วยเตือนกรณี JOIN แล้วแถวบวมหรือ GROUP BY ผิดระดับ แต่ไม่ได้พิสูจน์ว่ากลุ่มและค่าทุกแถวถูก |
| **held-out / paraphrase / novel** | strict EX ที่คำนวณแยกตามกลุ่มคำถามข้างต้น | ใช้บอกว่าระบบเก่งหรืออ่อนกับโจทย์ชนิดใด |
| **p50 latency** | เวลามัธยฐานต่อคำถาม | ครึ่งหนึ่งของคำถามเสร็จภายในเวลานี้ และอีกครึ่งช้ากว่านี้ |
| **p95 latency** | เวลาเปอร์เซ็นไทล์ที่ 95 | ประมาณ 95% ของคำถามเสร็จภายในเวลานี้ อีกประมาณ 5% ช้ากว่า |
| **± SD** | ส่วนเบี่ยงเบนมาตรฐานจากการรันซ้ำ 5 รอบ | ค่าน้อยหมายถึงผลระหว่างรอบค่อนข้างคงที่; ไม่ใช่ confidence interval |

#### ตัวอย่างเพื่อเข้าใจ `grain`

คำถามว่า “จำนวนนักเรียนแยกตามโรงเรียน” หากเฉลยมี 10 โรงเรียน จึงควรได้ 10 แถว:

- โมเดลได้ 47 แถวเพราะ JOIN ซ้ำ → `grain = false`
- โมเดลได้ 10 แถว แต่จับโรงเรียนผิดหรือตัวเลขผิด → `grain = true` ได้ เพราะ metric นี้ดูเพียงจำนวนแถว แต่ strict EX ยังเป็น false
- โมเดลได้ 10 แถวและทุกค่าเหมือนเฉลย → strict EX และ `grain` เป็น true

ดังนั้นชื่อ `grain correct` ในตารางควรตีความอย่างระวังว่า **row-count agreement** มากกว่าการยืนยันความถูกต้องเชิง semantic ทั้งหมด

#### ประเภทข้อผิดพลาด

| ประเภท | ความหมาย |
|---|---|
| `cols_only` | ผ่าน relaxed แต่ไม่ผ่าน strict; มักเป็นปัญหาคอลัมน์บรรยายเกิน ขาด หรือใช้ identifier คนละแบบ |
| `wrong_grain` | จำนวนแถวไม่เท่ากับเฉลย มักสัมพันธ์กับ JOIN หรือ GROUP BY ผิดระดับ |
| `wrong_result` | SQL รันได้และจำนวนแถวเท่ากัน แต่ค่าหรือคอลัมน์สำคัญไม่ตรง |
| `exec_fail` | มี SQL แต่รันไม่สำเร็จ แม้ผ่าน retry ที่อนุญาตแล้ว |
| `no_sql` | โมเดลไม่คืน SQL ที่ใช้ได้ |
| `exception` / `gold_error` | pipeline หรือการรัน SQL เฉลยเกิดข้อผิดพลาด |

### 3.4 ทำ ablation study

ทดลองสองตัวแปร โดยคงส่วนอื่นไว้เหมือนกัน:

| ตัวแปร | ค่าที่ทดลอง | คำถามที่ต้องการตอบ |
|---|---|---|
| `rag_top_k` | 0 และ 3 | การไม่ใส่ตัวอย่าง เทียบกับใส่ 3 ตัวอย่างที่คล้ายที่สุด ช่วยเท่าใด |
| `max_retries` | 0 และ 2 | การไม่ให้แก้ SQL เทียบกับให้แก้สูงสุด 2 ครั้ง ช่วยเท่าใด |

จึงได้ 4 config ได้แก่ `(rag=0,retry=0)`, `(0,2)`, `(3,0)` และ `(3,2)` แต่ละ config รันซ้ำ **5 รอบ** รอบละ **30 คำถาม** รวมเป็น **20 result files และ 600 question-runs** ทุก config ใช้ schema strategy แบบ `pruned`

## 4. ผลลัพธ์และการตีความ

**ใจความสำคัญ: RAG ทำให้ความแม่นยำเพิ่มขึ้นมาก ขณะที่ retry ไม่เพิ่ม strict EX; จุดอ่อนที่สุดคือโจทย์ novel และความไม่ตรงกันของคอลัมน์**

### 4.1 ผลของ config `rag=3, retry=2`

| Metric | ผลเฉลี่ย 5 รอบ | การตีความ |
|---|---:|---|
| EX strict | **47% ±4%** | result set ตรงกับเฉลยทุกแถวทุกคอลัมน์ประมาณครึ่งหนึ่ง |
| EX relaxed | **76% ±3%** | หากผ่อนปรนความต่างของคอลัมน์บรรยาย คำตอบประมาณ 3 ใน 4 ผ่าน |
| first-try | **44% ±4%** | คำตอบ strict ส่วนใหญ่ที่ผ่าน ทำได้ตั้งแต่ครั้งแรก |
| grain heuristic | **87% ±4%** | 87% มีจำนวนแถวเท่ากับเฉลย แต่ยังอาจมีค่าหรือกลุ่มผิดได้ |
| held_out strict EX | **48% ±4%** | ทำได้ระดับปานกลางกับข้อที่กันออกจาก RAG |
| paraphrase strict EX | **70% ±4%** | ทำได้ดีที่สุดกับคำถามที่เขียนใหม่จากแนวเดิม |
| novel strict EX | **12% ±11%** | ทำได้ต่ำและแปรปรวนสูงกับ metric × grain แบบใหม่ |
| p50 / p95 latency | **6.6 / 21.2 วินาที** | ค่ากลาง 6.6 วินาที แต่ tail latency สูงถึง 21.2 วินาทีที่ p95 |

| 3 | 2 | 5 | **47% ±4%** | 76% ±3% | 44% ±4% | 87% ±4% | 6.6s |

### 4.3 สิ่งที่ผลทดลองบอก

- **RAG เป็นปัจจัยหลัก:** เมื่อไม่เปิด retry การเพิ่ม `rag_top_k` จาก 0 เป็น 3 ทำให้ strict EX เพิ่มจาก **3% เป็น 47%** หรือเพิ่ม 44 percentage points และ relaxed EX เพิ่มจาก **30% เป็น 73%** แสดงว่าตัวอย่างเฉพาะโดเมนช่วยให้โมเดลเข้าใจ join path และ business rules ที่ schema อย่างเดียวสื่อไม่ครบ
- **Retry ช่วยน้อยมาก:** ที่ `rag=3` strict EX คงที่ **47% → 47%** ส่วน relaxed EX เพิ่ม 73% → 76% ซึ่งมีขนาดใกล้กับความแปรปรวนระหว่างรอบ และ p50 เพิ่ม 6.2 → 6.6 วินาที จึงยังไม่มีหลักฐานว่าคุ้มเปิดเป็นค่าเริ่มต้น
- **strict–relaxed gap ชี้ปัญหาการเลือกคอลัมน์:** ที่ config `rag=3,retry=2` มีช่องว่าง 29 percentage points ระหว่าง 47% กับ 76% หลายคำตอบจึงอาจได้ตัวเลขหรือโครงสร้างหลักถูก แต่คืนคอลัมน์บรรยายต่างจากเฉลย อย่างไรก็ตาม relaxed metric เป็น heuristic จึงควรตรวจตัวอย่างจริงก่อนสรุปว่างานธุรกิจใช้ได้ทั้งหมด
- **โจทย์ novel คือจุดอ่อนหลัก:** paraphrase 70% สูงกว่า held_out 48% และ novel 12% มาก แปลว่าระบบประยุกต์รูปแบบที่มีตัวอย่างใกล้เคียงได้ดี แต่ยังประกอบ metric กับระดับการจัดกลุ่มใหม่ได้ไม่ดี
- **ความไม่แน่นอนของ novel สูง:** `±11%` มาจากการรันซ้ำบนคำถาม novel เพียง 8 ข้อ จึงไม่ควรใช้ 12% เป็นค่าตายตัวสำหรับประชากรโจทย์ novel ทั้งหมด

### 4.4 การทดลองโมเดล DeepSeek ที่ไม่สมบูรณ์

มีการทดลอง `deepseek/deepseek-v4-flash-0731` ผ่าน OpenRouter 3 ครั้ง แต่ provider ค้างใกล้คำถามข้อ 29–30 และ runner เขียนไฟล์เมื่อครบทั้งชุดเท่านั้น จึงไม่มี result file ที่สมบูรณ์ ตัวเลขต่อไปนี้กู้จาก log เพียงบางส่วนและ **ห้ามเทียบตรงกับผลเฉลี่ย 5 รอบของ gpt-4o-mini**

| config | ข้อที่ทำเสร็จ | strict EX | relaxed EX | held_out | paraphrase | novel |
|---|---:|---:|---:|---:|---:|---:|
| rag=3, retry=2 | 27/30 | 67% | 93% | 44% | 75% | 83% |
| rag=0, retry=2 | 28/30 | 14% | 29% | 22% | 8% | 14% |

ผลบางส่วนยังเห็นทิศทางว่า RAG ช่วย แต่คะแนน DeepSeek โดยเฉพาะ novel อาจมี selection bias จากข้อที่รันไม่ครบ รวมทั้งเป็นเพียง partial run จึงใช้เป็น “สัญญาณสำหรับทดลองต่อ” ไม่ใช่ข้อสรุปว่าโมเดลนี้ดีกว่า

## 5. จุดแข็งและข้อจำกัด

**ใจความสำคัญ: การทดลองมี benchmark แยกและรันซ้ำ แต่ยังจำกัดด้วยขนาดชุดทดสอบ, heuristic metrics, ฐานข้อมูล dev และต้นทุนที่ไม่ได้เก็บ token จริง**

### จุดแข็ง

- **ประเมินแบบ end-to-end:** คำถามผ่าน retrieval, prompt, LLM, safety check และฐานข้อมูลจริง จึงสะท้อน pipeline ที่ผู้ใช้พบมากกว่าการตรวจ syntax อย่างเดียว
- **เปรียบเทียบผลลัพธ์แทนข้อความ SQL:** SQL สองชุดที่เขียนต่างกันแต่ให้คำตอบเดียวกันสามารถผ่านได้ ทำให้ metric สอดคล้องกับเป้าหมาย “ตอบคำถามถูก” มากกว่า exact string match
- **แยก benchmark จากคลัง RAG:** ลดความเสี่ยงที่ระบบได้เห็นข้อสอบตรง ๆ ผ่าน few-shot retrieval
- **ใช้ ablation ที่ตีความได้:** เปลี่ยน RAG และ retry เป็นตาราง 2×2 ทำให้ระบุได้ชัดว่าการเปลี่ยนแปลงใดสัมพันธ์กับคะแนนที่เพิ่มขึ้น
- **รันซ้ำ 5 รอบ:** รายงานค่าเฉลี่ยพร้อม SD ทำให้เห็นความผันผวนของ LLM แทนการเลือกผลจากรอบเดียว

### ข้อจำกัด

- **benchmark มีเพียง 30 ข้อ:** โดยเฉพาะ novel มี 8 ข้อ จึงครอบคลุมรูปแบบคำถามจริงได้ไม่มากและทำให้คะแนนย่อยแกว่งสูง
- **ทดสอบครบเพียงโมเดลเดียว:** ข้อสรุปหลักมาจาก gpt-4o-mini ส่วน DeepSeek รันไม่ครบ จึงยังสรุปเรื่อง model comparison ไม่ได้อย่างน่าเชื่อถือ
- **`grain` ตรวจเพียงจำนวนแถว:** จำนวนแถวเท่ากันอาจเกิดขึ้นทั้งที่ grouping key หรือค่าภายในผิด จึงไม่ควรเรียกว่า grain ถูกอย่างสมบูรณ์
- **relaxed EX อาจปล่อย false positive:** กฎเปรียบเทียบคอลัมน์แบบผ่อนปรนมีโอกาสให้ wrong metric ผ่านได้ในบางรูปแบบ จึงเหมาะเป็น diagnostic upper bound มากกว่าคะแนนหลัก
- **ฐานข้อมูลเป็น STS dev:** ผลอาจเปลี่ยนเมื่อข้อมูล production มีขนาด, distribution, null, edge case หรือช่วงเวลาต่างออกไป
- **ยังไม่มี confidence interval หรือ statistical test:** SD จาก 5 รอบบอกการกระจายของผลที่สังเกต แต่ยังไม่พอพิสูจน์ว่าความต่างเล็ก ๆ เช่น relaxed 73% กับ 76% มีนัยสำคัญ
- **ต้นทุนไม่ได้มาจาก usage log:** ตัวเลขค่าใช้จ่ายใช้ token budget โดยประมาณและมี uncertainty ราว ±50% ไม่รวม development/debugging runs

## 6. สรุปผล

**ใจความสำคัญ: เลือก `rag=3, retry=0` เป็นค่าเริ่มต้น และลงทุนกับคุณภาพตัวอย่าง/การเลือกคอลัมน์มากกว่าการเปิด retry**

- **สมมติฐานเรื่อง RAG ได้รับการสนับสนุน:** strict EX เพิ่มจาก 3% เป็น 47% และ relaxed EX เพิ่มจาก 30% เป็น 73% เมื่อเพิ่มตัวอย่างที่คล้ายกัน 3 ตัวอย่างโดยไม่เปิด retry ผลต่างมีขนาดใหญ่กว่าความผันผวนที่รายงานมาก
- **สมมติฐานเรื่อง retry ไม่ได้รับการสนับสนุนสำหรับ workload นี้:** ที่ `rag=3` strict EX ไม่เพิ่มจาก 47% และ latency เพิ่มขึ้น จึงไม่มีเหตุผลจากผลชุดนี้ให้เปิด retry เป็นค่าเริ่มต้น
- **config ที่แนะนำคือ `rag_top_k=3, max_retries=0`:** ให้ strict EX เท่ากับ config ที่เปิด retry คือ 47% แต่ p50 ต่ำกว่าเล็กน้อยและต้นทุนประมาณการต่ำกว่ามาก
- **ระบบยังไม่ควรถูกอธิบายว่าแม่นยำ 76% โดยไม่มีเงื่อนไข:** 76% คือ relaxed EX ซึ่งผ่อนปรนความต่างของคอลัมน์และอาจมี false positive ส่วนคะแนนหลัก strict EX คือ 47%
- **จุดลงทุนถัดไปชัดเจน:** เพิ่มตัวอย่างที่ครอบคลุมโจทย์ novel และบังคับให้คืนเฉพาะคอลัมน์ที่ผู้ใช้ถาม เพราะสองจุดนี้สอดคล้องกับ novel score ที่ต่ำและ strict–relaxed gap ที่กว้าง
- **ระดับความมั่นใจ:** มั่นใจสูงว่าการมี RAG ดีกว่าไม่มี RAG ภายใต้ benchmark นี้ แต่มั่นใจเพียงปานกลางต่อค่าคะแนนสัมบูรณ์และการนำไปใช้กับ production เนื่องจากชุดทดสอบเล็กและใช้ฐานข้อมูล dev

## 7. ข้อเสนอแนะ งานในอนาคต และค่าใช้จ่าย

**ใจความสำคัญ: ปรับ benchmark และระบบตาม error ที่พบ พร้อมเพิ่ม token logging เพื่อให้รายงานต้นทุนจริงแทนการประมาณ**

### 7.1 งานที่ควรทำต่อ

- **เพิ่มโจทย์ novel และตัวอย่าง RAG แบบเป็นระบบ:** novel มีเพียง 8 ข้อและได้ strict EX 12% จึงควรเพิ่มทั้ง benchmark novel และตัวอย่างที่ครอบคลุม metric × grain ที่ยังขาด แล้วรัน ablation ใหม่เพื่อวัดผล
- **ปรับ prompt/validator เรื่อง output columns:** ช่องว่าง strict–relaxed 29 points ชี้ว่าควรกำหนดให้คืนเฉพาะคอลัมน์ที่ผู้ใช้ถาม และอาจเพิ่ม deterministic post-processing เพื่อตรวจคอลัมน์เกิน
- **ปรับ metric `grain`:** เปรียบเทียบ grouping-key columns และ cardinality ต่อกลุ่ม ไม่ใช่ดู row count อย่างเดียว เพื่อให้ชื่อ metric ตรงกับสิ่งที่วัด
- **เพิ่ม per-question error analysis:** สรุปว่าข้อผิดเกิดจาก schema linking, join, filter, aggregation, value หรือ output columns เท่าใด เพื่อเลือกวิธีแก้ที่ตรงสาเหตุ
- **ทดสอบโมเดลที่สองผ่าน provider ที่เสถียร:** ใช้ direct API และต้องให้ครบ 30 ข้อ × 5 รอบภายใต้ config เดียวกัน ก่อนสรุปว่าโมเดลใดดีกว่า
- **ขยาย benchmark และทดสอบ production-like data:** เพิ่มจำนวนคำถาม, edge cases และช่วงข้อมูลหลายภาคเรียน เพื่อประเมิน generalization ได้ดีขึ้น

## 8. เฟส 2: จาก 1-Query Pipeline สู่ Conversational Agent (กันยายน 2026)

**ใจความสำคัญ: เปลี่ยนสถาปัตยกรรมตามข้อเสนอของอาจารย์ — agent loop รักษาความแม่นของ SQL ได้ และเพิ่มความสามารถที่ pipeline เดิมไม่มีเลย คือการถามกลับและปฏิเสธ**

### 8.1 ที่มาและสมมติฐาน

**ใจความสำคัญ: อาจารย์ชี้ว่าระบบเดิมไม่ใช่ agent — เป็นแค่ 1 query 1 output จึงทดลองเปลี่ยนเป็น loop แบบ ChatGPT/Gemini ที่ให้โมเดลเลือกเครื่องมือเอง**

- **Pipeline เดิม (เฟส 1):** คำถาม → ประกอบ prompt เดียว → LLM สร้าง SQL ครั้งเดียว → รัน → ตอบ โมเดลไม่มีทางเลือกอื่นนอกจากเขียน SQL ทุกครั้ง ไม่ว่าคำถามจะกำกวมหรือนอกขอบเขต
- **Agent ใหม่ (ADR 0006):** หนึ่ง Turn = โมเดลวนเลือกเครื่องมือเอง — `get_schema` (ดูโครงสร้างตาราง), `run_sql` (รัน SQL อ่านอย่างเดียว) และ `final_answer` (ส่งคำตอบ ซึ่งบังคับให้เลือกได้ 3 แบบ: **result / clarification / refusal**) เซิร์ฟเวอร์ไม่เก็บความจำ — ผู้เรียกใช้ส่งประวัติบทสนทนามาเอง และมีเพดาน 8 steps ต่อ Turn เพื่อกัน loop ไม่รู้จบ
- **สมมติฐาน:** agent loop จะ (1) ไม่ทำให้ความแม่นยำ SQL แย่ลงอย่างมีนัยสำคัญ และ (2) ปลดล็อกการถามกลับ/ปฏิเสธที่ pipeline ทำไม่ได้เลย

### 8.2 Benchmark ใหม่ที่สมดุล (ADR 0007)

**ใจความสำคัญ: ชุดทดสอบ 30 ข้อเดิมกระจุกอยู่ที่คำถามนับ/กรอง และไม่มีโจทย์วัดการถามกลับหรือปฏิเสธเลย จึงสร้างชุดใหม่ 36 ข้อที่กระจายเท่ากัน 4 ข้อต่อ 7 ประเภท**

- **28 ข้อ SQL** กระจายเท่า ๆ กัน (4 ข้อ × 7 buckets): นับ+จัดกลุ่ม, นับ+กรอง+จัดกลุ่ม, รวม/เฉลี่ย, สัดส่วน, เงื่อนไข HAVING, ช่วงเวลา และอันดับ — ทุกข้อผ่านการรันจริงกับฐานข้อมูลเพื่อยืนยันเฉลย
- **4 ข้อถามกลับ** (คำถามกำกวม เช่น "เด็กเสี่ยงมีเท่าไหร่" ไม่ระบุ tier) + **4 ข้อปฏิเสธ** (ขอข้อมูลส่วนบุคคล เช่น เบอร์ผู้ปกครอง / คำสั่งเขียนข้อมูล) — ให้คะแนนตาม **ประเภทคำตอบ** ไม่ใช่ SQL
- ตัวอย่างในคลัง RAG ก็ปรับสมดุลตามเพดาน 8 ตัวอย่างต่อ bucket เพื่อไม่ให้ retrieval บิดเอียง

### 8.3 ผลเปรียบเทียบ Before / After

**ใจความสำคัญ: SQL ได้ parity, ความสามารถใหม่ได้ 8/8, แลกด้วย latency ~4 เท่า**

| Metric | Pipeline (before) | Agent (after) | การตีความ |
|---|--:|--:|---|
| strict EX (SQL 28 ข้อ) | 57.1% | 53.6% | ต่าง 1 ข้อ — อยู่ในระดับ noise ของ single-run, ไม่มีนัยสำคัญ |
| relaxed EX | 75.0% | 71.4% | เช่นเดียวกัน |
| grain (จำนวนแถวถูก) | 92.9% | 92.9% | เท่ากันเป๊ะ |
| **ถามกลับเมื่อกำกวม** | **0/4** | **4/4** | pipeline ไม่เคยถามกลับเลย |
| **ปฏิเสธนอกขอบเขต** | **0/4** | **4/4** | รวมปิด PII leak: ขอเบอร์ผู้ปกครองแล้วเดิมยอมเขียน SQL |
| STEP_BUDGET_EXCEEDED | — | 0 ข้อ | loop จบสะอาดทุกข้อ |
| latency p50 (SQL) | 2.3 s | 10.5 s | agent ใช้ ~2.2 steps/คำถาม |
| latency p95 (SQL) | 9.3 s | 16.1 s | tail ยังใกล้เคียงกัน |

รายละเอียด per-bucket อยู่ใน `eval/sts/BEFORE_AFTER.md`

### 8.4 การปรับจูนที่ทำให้ถึง 8/8

**ใจความสำคัญ: ชัยชนะมาจากการจัดลำดับกติกาใน prompt ไม่ใช่การจูนตัวเลข**

- รอบแรกได้ clarify 3/4 เพราะ system prompt วางกติกาการถามกลับไว้ท้ายสุด และบอกให้ "รัน SQL ทันที" ขึ้นหัว — โมเดลจึงกดความกำกวมทิ้งและตอบเลย
- แก้ 2 จุด: (1) ยกกติกา **"จำแนกประเภทคำถามก่อนเขียน SQL เสมอ"** ขึ้นเป็นลำดับแรก และ (2) ใส่ **คู่เทียบตัวอย่าง** คำถามกำกวม (ขาด tier หรือช่วงเวลา → ถามกลับ) กับคำถามครบสาระ (มีครบ → ตอบด้วย SQL ได้เลย) พร้อมกติกาเจาะจงว่าคำบอกเวลาแบบเปรียบเทียบ ("ล่าสุด", "ช่วงนี้") ที่ไม่มีวันที่ = ถามกลับ แต่ "ปัจจุบัน" ที่มีนิยามในโดเมน = ไม่กำกวม
- หลังแก้: **4/4 ถามกลับ และ 4/4 ปฏิเสธ โดยไม่มี over-clarification** — คำถาม SQL ทั้ง 28 ยังถูกตอบด้วย SQL ทุกข้อ กติกาไม่ได้ลามไปกวาดคำถามปกติ
- หยุดจูนหลัง 3 รอบเพื่อไม่ overfit prompt กับโจทย์ 4 ข้อ

### 8.5 บั๊กสำคัญที่ eval จับได้

**ใจความสำคัญ: การวัดแบบ end-to-end จับบั๊กที่ unit test มองไม่เห็น 2 ตัว**

1. **Tool spec ไม่เคยถูก bind ให้โมเดล:** mock ใน unit test หลอกว่ามี tools ทำให้เทสผ่านหมด แต่โมเดลจริงไม่เห็น tool เลย จึงพิมพ์ข้อความยาวจนหมด 8 steps แล้วตายด้วย STEP_BUDGET_EXCEEDED — จับได้จาก smoke run จริงแรก แก้แล้วมี regression test คอย
2. **คำถามแรกของ session หลุดไป pipeline เก่า:** route เช็ค `if history:` ทำให้ประวัติว่าง (Turn แรก) ไม่เข้า agent — แก้เป็นเช็คว่า field ถูกส่งมาหรือไม่ (ส่ง `[]` = เป็น Turn แบบสนทนา, ไม่ส่ง = โหมดเดิม) จึง backward compatible

### 8.6 ข้อจำกัดของการเทียบครั้งนี้

- รันครั้งเดียวต่อเอนจิน (n=4 ต่อ bucket แกว่งสูง) — สรุประดับรวมเท่านั้น
- รอบ agent ใช้ concurrency 1 เพื่อเลี่ยง rate limit (รอบแรกโดน 429 ทำให้ 9 ข้อ fail และถูกทิ้ง) — ความล่าช้ารวมไม่ได้เทียบข้ามโหมดโดยตรง
- กติกาป้องกัน over-clarification อาศัยตัวอย่างใน prompt ซึ่งยังไม่ผ่านการพิสูจน์เชิงสถิติ — ควรขยายชุด ambiguous ต่อ

### 8.7 สรุปเฟส 2 สำหรับสไลด์

- **สถาปัตยกรรมเปลี่ยนจริง:** จาก "1 คำถาม 1 SQL" เป็น agent loop ที่โมเดลเลือกเครื่องมือเอง ตามข้อเสนอของอาจารย์
- **ความแม่นยำ SQL ไม่หาย:** strict EX ต่างกัน 1 ข้อใน 28 — parity ภายใต้ noise
- **ความปลอดภัยและ UX กระโดด:** ปฏิเสธคำขอข้อมูลส่วนบุคคล/คำสั่งเขียนข้อมูล 4/4, ถามกลับเมื่อกำกวม 4/4 (เดิม 0 ทั้งคู่)
- **ราคาที่จ่าย:** p50 latency ~4 เท่า (2.3 → 10.5 วินาที) จากโครงสร้าง multi-step — เป็นทางเลือกเชิงออกแบบ ไม่ใช่ข้อบกพร่อง
- **งานต่อยอด:** ขยายชุด ambiguous/refusal, ลด latency (cache schema, ย่อ step), และวัด token cost จริงของ agent
